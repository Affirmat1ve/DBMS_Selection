Для работы над ответом я использовал deepseek актуальный на момент октября 2025. Первично нейронке был задан базовый вопрос "какую СУБД следует выбрать если требования формулируются как список", потом по отдельным вопросам были заданы уточняющие, а также некоторые пункты я гуглил самостоятельно.

Необходимо спроектировать систему для кассовых терминалов крупной торговой сети.

Требования:
- мгновенная обработка тысяч мелких транзакций одновременно;
- целостность данных (остатки на складе не должны уходить в минус);
- строгая консистентность (списанные бонусы сразу отражаются в системе лояльности)

 Вопросы для ответа
1. Какие ключевые требования к СУБД в этом кейсе?
	1. БД должна быть производительной и отзывчивой
	2. важно иметь возможность восстановить состояние при сбоях (потому что отменить продажу будет очень сложно)
	3. поскольку кассовые терминалы находятся в разных магазинах, требуется согласованность их данных (либо согласованность локальных БД, либо БД должна быть изначально централизованной)
2. Какие сложности или ограничения могут возникнуть при выборе СУБД?
	1. лицензирование может стать проблемой (не всё можно без проблем купить сейчас)
	2. частое обращение к состоянию склада сильно задержит его работу (нейронка называет это Hot Rows), проблема распространенная, так что выбранная СУБД обязательно должна иметь механизм работы с подобной задачей
	3. поскольку заказчик - торговая сеть (а не профильная ИТ компания), решение должно быть распространенным, чтобы всегда можно было найти специалистов на рынке труда (а не выращивать их самостоятельно)
3. Какие классы СУБД подходят для решения задачи?
	1. работаем с транзакциями - значит реляционная OLTP, не думаю что есть смысл усложнять, поскольку это индустриальный стандарт (отсылаюсь на упомянутую мной сложность с поиском специалистов)
4. Приведите примеры конкретных СУБД, которые вы бы выбрали.
	1. PostgreSQL
	2. oracle DB
	3. Microsoft SQL Server
5. Обоснуйте ваш выбор: почему именно эта СУБД?
	1. PostgreSQL - самый очевидный выбор (наиболее распространенная из open-source)
	2. oracle DB- лучшее что можно купить за деньги (если есть желание и возможность заплатить за лицензию)
	3. Microsoft SQL Server - предложение нейронки для (почти цитирую) "глубокой интеграции со стеком Microsoft: Отличная совместимость с .NET, Azure, Visual Studio." Выбор специфичный (по моему мнению, лично с этим никогда не сталкивался, но Microsoft уж точно не корпорация добра). Если упомянутая совместимость будет полезна - можно рассмотреть.
6. Какие риски или проблемы могут возникнуть при эксплуатации выбранной СУБД?
	1. мой фаворит PostgreSQL - требует тонкой настройки, для этого придется содержать специалистов. Также очень важно кропотливо составить архитектуру решения, поскольку позже изменить решение будет дорого (по CAP-theorem мы хотим консистентность и доступность, так что делимость будет крайне слабой)
